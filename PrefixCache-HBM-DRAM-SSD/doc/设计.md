# PrefixCache HBM / DRAM / SSD 评测

## 目的

在昇腾 910C 单机单卡、vLLM/vLLM-Ascend 0.23.0 和 Mooncake 环境中，对完全相同的
16K P1 请求比较四个阶段的 TTFT：

- `R1-warmup`：HBM 和外部 Prefix Cache 均未命中的冷请求；
- `R2-hbm-cache`：vLLM 本地 HBM Prefix Cache 命中；
- `R3-dram-cache`：本地 HBM 未命中，从 Mooncake DRAM 恢复；
- `R4-ssd-cache`：本地 HBM 和 Mooncake DRAM 均未命中，从 Mooncake SSD 恢复。

正式入口只有两段代码：

```bash
bash StartUp.sh
bash Run-all
```

`StartUp.sh` 一次性开启 DRAM + SSD 分层能力，执行 R1～R4 的过程中不切换 SSD
开关。`Run-all` 负责逐阶段验证来源并生成同一个结果文件。服务器上无需存在这两个
文件：窗口一完整粘贴 `StartUp.sh` 内容并保持运行，窗口二完整粘贴 `Run-all` 内容即可。
两段代码通过 `/tmp/mooncake.json` 及仅本次启动 PID 可用的状态/请求文件通信；测试端
自动完成保留 SSD 的运行时重启，不需要再次粘贴启动代码。

`Run-all` 是专为终端粘贴生成的压缩入口：内含 SHA256 完整性校验，粘贴被截断
或改写时会在执行评测前直接报错。可维护源码保存在 `Run-all.payload`，修改后用
`python3 tools/build_run_all_wrapper.py` 重新生成入口；使用者仍只需粘贴 `Run-all`。

## 为什么来源判定可靠

不能仅靠 vLLM 的 `external_prefix_cache` 命中判断 DRAM/SSD，因为该指标只表示命中
外部 Prefix Cache，不包含 Mooncake 存储层级。

本测试联合使用五类证据：

1. P1 身份：捕获实际 prompt，校验 token 数、全文 SHA256、token SHA256 和首个
   128-token block SHA256；R1～R4 必须完全一致。
2. vLLM 路径：使用阶段前后的 local/external token counter 增量，区分 HBM 与外部
   Prefix Cache，并排除重算。
3. Mooncake 存储状态：使用 master 导出的 DRAM/SSD allocated bytes，确认 R3 有 DRAM
   驻留、每个 R1 的 SSD 写入已稳定完成；R3 后先等待读租约释放和后台 SSD 写盘完成，再受控重启 master
   和 vLLM，但保留同一个 SSD 会话目录，并要求新实例恢复重启前的 SSD 字节数和 Key。
4. 进程级物理读：阶段前后汇总 `StartUp.sh` 及其全部 Mooncake/vLLM 子进程的
   `/proc/<pid>/io` `read_bytes`。R3 必须为 0；R4 必须覆盖该 batch 的完整可缓存
   SSD 副本量。其他容器的磁盘流量不会进入该计数。
5. 设备级物理读：R4 前后读取 `/sys/class/block/<kname>/stat` 的 read sectors，要求
   已验证 NVMe 的读取增量不小于上述进程读量。启动时以 O_DIRECT 探针验证容器
   overlay 确实映射到该设备；每次 R4 前对本会话 SSD 文件执行 `fsync` 和
   `POSIX_FADV_DONTNEED`；脚本等待该 batch 的 SSD 分配量新增且稳定，并将实际新增量作为 R4
   进程物理读下限；最后用
   设备扇区增量防止部分页缓存冒充完整 SSD 命中。

阶段硬条件如下：

| 阶段 | vLLM 条件 | Mooncake tier 条件 | 结论 |
|---|---|---|---|
| R1 | local、external 均 ≤ 5% | 无读取层级要求；SSD 副本必须完成 | MISS |
| R2 | local 覆盖全部可缓存 block | 不参与来源判定 | HBM |
| R3 | local ≤ 5%，external 覆盖全部可缓存 block | DRAM allocated bytes > 0；评测运行时进程物理读增量 = 0 | DRAM |
| R4 | local ≤ 5%，external 覆盖全部可缓存 block | 受控重启已清空 HBM/DRAM；重启后 DRAM allocated bytes = 0，SSD 字节数和 Key 均已恢复；运行时进程物理读 ≥ 本 batch 完整可缓存 SSD 副本量；NVMe read bytes ≥ 进程读量 | SSD |

默认 16K 输入、128 block 时，“全部可缓存 block”的最低 token hit rate 为
`(16384-128)/16384 = 99.21875%`，比通用的 95% 下限更严格；最后一个 block 不作为
可复用 Prefix Cache。修改输入长度或 block size 后脚本会自动重算该门槛。

不能用 DRAM 新增字节数推算每个 batch 必须新写入的 SSD 字节数。Mooncake 按 KV
block 去重，不同的 P1 请求仍可能共享已落盘 block；第二批因此新写入 110
个而非 126 个 block 仍是正常的。脚本要求当批有实际、稳定的 SSD 新写入；R4 再通过重启后 DRAM 为
0、固定 P1 的外部全量命中、清文件页缓存和两级物理读来完成严格来源判定。

当前 Mooncake 虽然在内部定义了 cache-hit 计数器，但没有将它们序列化到 HTTP
`/metrics`，且该版本没有 hit-bytes 指标。因此脚本只使用该版本实际导出的指标：

```text
master_allocated_bytes
master_allocated_file_size_bytes
```

零值指标可能暂时不出现在 `/metrics`，所以脚本在 R1 写入后检查分配量，并在重启后将
“SSD 指标和 Key 可读但 DRAM 指标缺失”按 DRAM 零分配处理。
指标缺失、进程或块设备统计不可读、R3 观察到进程物理读，或 R4 没有观察到两级物理
读取，都会直接失败。若 R4 实际仍从 DRAM 命中，来源会打印为
`DRAM` 或 `MISS_OR_MIXED`，该 batch 的 R4 被标为无效并从 Summary 排除；严格模式
默认返回退出码 2。

这些指标是 master 的全局计数器，正式评测期间不能向同一套 vLLM/Mooncake 实例发送
其他业务请求，否则其他流量会污染阶段增量。

## 每种并发的执行流程

```text
Phase A：对每个 batch 依次执行
  清 HBM，保留 Mooncake
    -> R1：发送全新 P1，验证冷请求
    -> 等待本 batch 的 eager SSD 写入新增且稳定
    -> R2：重放 P1，验证 local HBM 命中
    -> 清 HBM
    -> R3：重放 P1，验证外部命中且运行时进程物理读为 0

Phase B：本并发的所有 R3 完成后
  等待 12 秒 R3 读租约释放，等待后台 SSD 写盘稳定
  Run-all 向窗口一粘贴运行的启动管理器发送受控重启请求
    -> 停止 vLLM 和 mooncake_master，保留本次 SSD 会话目录
    -> 用完全相同的参数和 SSD 目录启动新一代 master/vLLM
    -> 验证 DRAM 为 0，SSD 分配量和 Key 不少于重启前
    -> 对每个 batch：清 SSD 文件页缓存 -> R4 -> 验证进程物理读及 NVMe 物理读
```

Mooncake 以 eager 模式运行：R1 写入完成后，P1 同时拥有 MEMORY 与 LOCAL_DISK 副本。
R3 的读取选择 MEMORY。随后停止进程会直接释放 HBM 和 DRAM，不再生成数百 GB 的
压力请求；启动管理器只在整个测试结束、失败或中断时删除 SSD 会话目录，中间重启不会
执行最终清理。新 master 从同一个隔离目录恢复 SSD 元数据，脚本在 R4 前验证 SSD
分配量、Key 和 DRAM 零分配均稳定。

“重启恢复成功”仍不是 R4 来源的唯一依据。每个 R4 都必须同时满足 local 未命中、
external 全量命中、进程物理读覆盖该 batch 完整可缓存数据量、NVMe 读量覆盖进程读量；
任一证据不足都会失败关闭，不会把 DRAM、页缓存或重算误报成 SSD。

## P1 请求设计

当前默认测试 C1、C5、C10，每种并发执行 5 个 batch：

| 并发 | 每批请求 | batch 数 | 唯一 P1 请求数 | 四阶段总推理数 |
|---|---:|---:|---:|---:|
| C1 | 1 | 5 | 5 | 20 |
| C5 | 5 | 5 | 25 | 100 |
| C10 | 10 | 5 | 50 | 200 |
| 合计 |  |  | 80 | 320 |

同一 batch 内、不同 batch、不同并发之间的 P1 都必须唯一；同一个 `prompt_id` 在
R1～R4 中必须完全相同。每条请求的第一个 128-token block 也必须唯一。

## 启动配置

`StartUp.sh` 会：

- 为本次会话创建新的空 SSD 子目录，避免旧数据污染 R1；
- 使用 `findmnt` 和 `lsblk` 验证路径位于本地非旋转块设备，拒绝 tmpfs、非块设备和
  旋转盘；容器 overlay 仅在显式指定后端块设备并通过 O_DIRECT 映射探针后放行；
- 在 `mooncake.json` 中设置 `enable_ssd_offload=true` 和 `ssd_offload_path`，并显式设置
  `MOONCAKE_OFFLOAD_FILE_STORAGE_PATH` 为同一会话目录、使用可重启扫描恢复的
  `bucket_storage_backend`；
- 使用 `--enable_offload=true --offload_on_evict=false` 启动 master；
- 使用 `--promotion_on_hit=false`，避免 R4 首次 SSD 命中后自动提升到 DRAM；
- 设置 `load_async=false`，让正式评测采用更保守、容易观测的同步 SSD 回填路径；
- 要求 `mooncake-transfer-engine-npu==0.3.12.post1`，并校验 Python 模块与
  `libmooncake_store.so` 均来自新版 wheel；该版本已移除 16K 回填触发的
  `kMaxSliceSize` 断言；
- 设置 `MOONCAKE_OFFLOAD_USE_URING=0`，避开当前 Ascend 驱动与 host buffer 的
  `io_uring_register_buffers` 不兼容；R4 由逐文件页缓存清理和物理 I/O 双计数保证；
- R1 不再以“SSD 有新增”作为成功条件：SSD 新增字节必须完整覆盖该批 DRAM KV 字节，
  否则立即停止，不进入会产生部分命中的 R4；
- 记录 SSD 的 kernel block name，供 `Run-all` 对 R4 的设备 read sectors 做增量校验；
- 记录启动管理器的 PID 和进程启动时钟，供 `Run-all` 汇总 Mooncake/vLLM 进程树的
  物理读取，并防止 PID 被复用后误发信号；
- 建立 `signal-request-v1` 控制协议。`Run-all` 只能向配置中与启动 PID 严格匹配的
  `/tmp/mooncake-benchmark-<PID>.request` 原子写入请求，并向同一 PID 发送 `SIGUSR1`；
  启动管理器负责重启、逐代写状态及保留 SSD，会话最终清理由原有 trap 统一执行；
- SSD staging buffer 默认 `4096MB`，覆盖 Qwen3-8B 单条 16K BF16 KV，不按
  并发数成倍预留 `aclrtMallocHost` buffer。
- vLLM 保持加入 SSD 前的基线配置：`max-model-len=32768`、
  `gpu-memory-utilization=0.9`，确保 HBM/DRAM/SSD 结果可比。
- 同时清理当前和旧版 vLLM 的 `VLLM::EngineCore` / `VLLMEngineCore` 进程名，等待 NPU
  物理页释放，并在启动前打印 `npu-smi info`，避免残留 EngineCore 占用 HBM。

默认 SSD 根目录为 `/mnt/mooncake-ssd-offload`。可在启动前覆盖：

```bash
MOONCAKE_SSD_ROOT=/mnt/nvme/mooncake \
MOONCAKE_SEGMENT_GB=256 \
MOONCAKE_SSD_BUFFER_MB=4096 \
MOONCAKE_SSD_QUOTA_GB=3072 \
bash StartUp.sh
```

当前 A3 容器继续使用加入 SSD 前已经验证过的非 Fabric Memory 路径。`StartUp.sh`
会在其子 Shell 内自动设置 `ASCEND_BUFFER_POOL=4:8`，这是 vLLM-Ascend 对 A3
非 Fabric 路径建议的中转模式；它避免把 256GB DRAM 段和 SSD staging buffer
直接映射进 ADXL。如确有需要，可用
`MOONCAKE_ASCEND_BUFFER_POOL=数量:大小MB` 覆盖，但正式评测不允许设为 `0:0`。

### 启动故障复盘：Ascend 507899

故障现象是加入 SSD 后 vLLM 在 EngineCore 初始化阶段退出，Ascend 报
`aclrtMallocPhysical 507899` 或 `aclrtGetMemInfo 507899`；同一环境使用加入 SSD 前的
HBM/DRAM 启动脚本正常。完整脚本直接粘贴到 Shell 与执行脚本文件的结果相同，外层包装
子 Shell 不是故障原因。

最终日志给出了以下证据链：

1. vLLM 已打印 `Available KV cache memory`，并成功创建、注册全部 NPU KV tensor；
2. 随后才打印 `NPU KV cache allocated; initializing Mooncake DRAM/SSD now`，证明此时
   NPU KV 分配顺序已经正确；
3. Mooncake 为 SSD staging buffer 调用 `aclrtMallocHost`，然后
   `io_uring_register_buffers` 对该 4GB buffer 返回 `errno=14 (Bad address)`；
4. Mooncake 虽打印会 fallback 到 non-fixed-buffer io_uring，但紧接着第一次
   `aclrtGetMemInfo` 仍返回 507899，说明当前 Ascend 驱动上下文已无法继续使用。

因此主要根因不是 SSD 路径、3TB quota、HBM 容量或启动包装脚本，而是当前 Ascend
运行时与 Mooncake 的 fixed-buffer io_uring 注册不兼容。之前将 Mooncake 初始化延后到
NPU KV 分配之后是必要的隔离措施：它既避免 SSD host memory 抢占 NPU KV 初始化资源，
也证明最终 507899 出现在 io_uring 注册之后；但只调整初始化顺序不足以解决该问题。

最终修复同时保留两项措施：

- 通过只在本次进程树生效的临时 Python import hook，保持“先分配并注册 NPU KV，
  再初始化 Mooncake DRAM/SSD”；scheduler client 和容器内安装文件不变，退出时删除 hook；
- 显式设置 `MOONCAKE_OFFLOAD_USE_URING=0`，使 Mooncake 使用稳定的 POSIX
  `pread/pwrite` 路径，完全避开出错的 `io_uring_register_buffers`。

R4 的首次 SSD 回填固定关闭 `load_async`，使来源判定和 TTFT 统计覆盖完整的同步 SSD
回填。此前 EngineCore 退出的直接原因不是异步传输竞态，而是旧 Mooncake
`file_storage.cpp` 的 `sizes[i] <= kMaxSliceSize` 断言；仅关闭异步加载不能修复。
正式 SSD 评测因此同时要求 Mooncake 0.3.12.post1，并在启动前验证实际导入路径和动态
库来源，防止 CANN 内置旧版覆盖 pip 安装的新版。`StartUp.sh` 同时把每一代 vLLM 的
标准输出和错误保留在 `/tmp/vllm-ssd-<启动PID>-g<代数>.log`，即使重启失败也可定位
具体代数。

关闭 Mooncake io_uring 不会把页缓存误判为 SSD：启动阶段仍用 O_DIRECT 探针证明
容器 overlay 映射到指定 NVMe；每个 R4 batch 前逐文件 `fsync` 并执行
`POSIX_FADV_DONTNEED`，随后要求评测进程物理读量覆盖该 batch 的完整可缓存 SSD
副本量，且 NVMe read sectors 增量不小于进程读量。任一条件不满足，R4 都会失败关闭。

修复后的启动日志应包含：

```text
启动脚本版本：restart-preserve-ssd-v2
SSD I/O=POSIX
```

并且不应再出现 `SharedUringRing` 或 `io_uring_register_buffers failed`。

默认 SSD staging buffer 为 4096MB。Qwen3-8B 单条 16K BF16 KV 约 2.25GB，
Mooncake 接收线程逐请求恢复，因此 4GB 可覆盖单条 R4，无需随并发度线性扩大
buffer。过小会在 R4 产生 `BUFFER_OVERFLOW`，过大只会增加每个 rank 的
主机内存占用。

如 NPU 容量不同，可在粘贴/执行前覆盖 `VLLM_MAX_MODEL_LEN` 和
`VLLM_GPU_MEMORY_UTILIZATION`；`Run-all` 默认 16K 输入时，前者必须大于 16384。

当前评测容器默认使用 `/mnt/mooncake-ssd-offload`，并将已确认的
`/dev/nvme3n1p1` 作为 overlay 后端，因此可以直接启动：

```bash
bash StartUp.sh
```

也可以按实际使用方式，在窗口一把 `StartUp.sh` 的完整内容直接粘贴到登录终端执行，
再在窗口二完整粘贴 `Run-all`。启动代码自带最外层子 Shell，只有粘贴到最后的 `)` 后
才开始运行；内部 `exit` 或清理 trap 不会退出 SSH 登录 Shell。必须复制完整内容，不能
漏掉开头的 `(` 或结尾的 `)`。窗口二不需要知道或保存启动代码，重启请求由窗口一仍在
运行的子 Shell 接收并完成；因此全流程仍然只是“两次粘贴”，不是两次启动。

迁移到其他容器时，可以用 `MOONCAKE_SSD_ROOT` 和 `MOONCAKE_SSD_BLOCK_DEVICE` 覆盖
这两个默认值。

脚本会先对会话目录执行 256MiB O_DIRECT 写入和读取，并要求指定块设备的 write/read
sectors 分别至少增加 256MiB。探针失败时仍拒绝启动，不能仅凭环境变量绕过校验。
容器只暴露 NVMe 的 sysfs、没有 `/dev/nvme*` 设备节点也可以验证；脚本通过 `lsblk`
的 KNAME 和 `/sys/class/block/<kname>/stat` 获取设备属性与 I/O 计数，不会直接打开裸盘。

SSD 路径必须是已经挂载的真实 SSD 文件系统。每次启动会先清理由旧版本遗留的
`session-*` 缓存目录，再创建新的 `session-时间-PID` 子目录。

`Run-all` 默认在成功、失败或中断退出时通知启动管理器停止 vLLM/Mooncake，并删除
本次 SSD 会话目录；R3 到 R4 的中间重启明确绕过该删除逻辑。单独终止窗口一的启动
管理器也会触发最终清理。这里只删除
SSD KV Cache，`vb-result/` 下的 JSON、Excel、manifest 等评测结果会保留。需要在失败后
保留运行现场调试时，可显式设置：

```bash
VB_CLEANUP_AFTER_RUN=0 bash Run-all
```

Mooncake SSD offload 需要安装版本支持 `enable_ssd_offload`、`ssd_offload_path` 以及
上述 tier metrics。能力不足时启动或评测会明确失败，不会降级为不可靠判定。

```bash
VB_BATCHES=5
VB_INPUT_LEN=16384
VB_BLOCK_SIZE=128
VB_BASE_SEED=314159
VB_MIN_HIT_RATE=0.95
VB_MAX_MISS_RATE=0.05

VB_STRICT=1

VB_MOONCAKE_PROMETHEUS_URL=http://127.0.0.1:9003/metrics
```

硬条件，脚本立即失败。该超时包含 Mooncake、模型和 NPU KV Cache 的完整重新启动时间；
不能关闭 R4 tier 校验。

## 输出

默认结果目录为北京时间命名的 `vb-result/YYYY-MM-DD HH-MM-SS/`，包括：

- `vb-result.xlsx`；
- `C1-result.json`、`C5-result.json`、`C10-result.json`；
- `json/C*/R*/` 原始 vLLM 详细结果；
- `p1-manifest.json` 和 `p1-prompts.jsonl`；
- `session.json`。

Excel Sheet 顺序为：

1. `Summary`；
2. `R1-warmup`；
3. `R2-hbm-cache`；
4. `R3-dram-cache`；
5. `R4-ssd-cache`；
6. `validation`；
7. `P1-manifest`。

Summary 同时提供 R3/R2、R4/R2 和 R4/R3 的绝对及百分比劣化。`validation` 保存每个
stage/batch 的 local/external 命中率、Mooncake valid gets、DRAM/SSD hits、bytes、
SSD block-device read bytes、
最终来源、有效性和判定依据。执行过程中也会打印 `KV来源=HBM/DRAM/SSD` 及简要依据。

## 容量注意事项

Mooncake DRAM 必须至少能容纳当前一个 P1 batch，否则 R3 无法形成纯 DRAM 基线。
Qwen3-8B BF16 KV 按约 2.25GB/条 16K 请求估算，当前 C10 单批约 22.5GB，
默认 256GB DRAM 段可留出充足余量；主机仍需为 vLLM、SSD buffer、Mooncake 元数据和操作系统预留内存。

SSD quota 必须能容纳全部 P1 副本。默认磁盘 eviction policy 为 `none`：
空间不足时宁可失败，也不允许静默删除 P1 后把 R4 变成重算。
当前 C1/C5/C10 按 Qwen3-8B 估算约需 180GB 可用 SSD 空间；
`StartUp.sh` 默认 quota 为 3072GB，并在启动前校验文件系统可用空间。3072GB 是容量
上限和启动前的可用空间门槛，不是需要永久保留的评测结果；本次运行退出清理后，SSD
KV Cache 文件会被删除并归还空间。
